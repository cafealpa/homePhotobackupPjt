# 얼굴별 LanceDB 검색 인덱스와 인물 후보

한 사진에 여러 사람이 있는 것을 기본으로 한다. 사진 하나당 하나의 얼굴 벡터로 합치지 않고,
SQLite `faces.id`를 키로 각 얼굴을 LanceDB에 저장한다.

| face_id | asset_id | 의미 |
|---|---|---|
| 11 | 1 | 사진 1의 첫 번째 얼굴 |
| 12 | 1 | 사진 1의 두 번째 얼굴 |
| 21 | 2 | 사진 2의 첫 번째 얼굴 |
| 22 | 2 | 사진 2의 두 번째 얼굴 |

얼굴 11과 12는 서로 다른 벡터로 조회하며 서로 다른 후보를 반환할 수 있다.
검색 결과에서도 `face_id`를 유지한다. 같은 사진에 있는 후보 얼굴들을 사진 ID로 합치지 않는다.

## 저장 경계

- SQLite: 기존 512차원 얼굴 벡터, 얼굴 위치, 사진 연결, 확정 인물 ID, 이름, 군집 ID, 숨김 상태의 기준.
- LanceDB 얼굴 테이블: face_id, asset_id, 벡터 SHA-256 fingerprint, 정규화된 512차원 벡터.
- 장면 검색(SigLIP 2)은 별도 테이블을 그대로 사용한다. 얼굴/장면 벡터는 서로 비교하지 않는다.
- 현재 고정 InsightFace buffalo_l 워커가 만든 기존 벡터를 복제하므로 새 모델이나 GPU가 필요하지 않다.
- 기존 DB에 모델 리비전이 없어서 `legacy-insightface-buffalo_l-512-v1`이라는 별도 식별자를 사용한다.
  임의의 다른 512차원 모델과 호환된다는 뜻이 아니다. 얼굴 모델 변경 시 출처 관리 및 인덱스 재구축이 필요하다.

## 동기화

기존 로컬 검색 서비스와 같은 프로세스에서 얼굴 동기화 스레드를 따로 실행한다.
장면 임베딩 전체 분석이 끝나기를 기다리지 않는다. 실행 설정은 [로컬 검색 안내](MCP-SEMANTIC-SEARCH.md)와 같다.

`GET /api/v1/internal/search/faces?afterId=0`에서 얼굴 ID 순으로 100개씩 읽는다.
API 키로 인증하며 비활성·숨김 얼굴의 벡터는 전송하지 않는다. 변경 없는 벡터는 다시 저장하지 않는다.
전체 순회 후 5분 간격으로 반복한다. 새 얼굴은 새로 저장하고, 숨김·삭제·재분석된 얼굴을 반영한다.

얼굴 재분석은 SQLite 얼굴 행을 제거할 수 있으므로, **전체 목록 순회에 성공했을 때만**
목록에서 사라진 얼굴을 인덱스에서 정리한다. 실패·중단한 순회에서는 일괄 정리하지 않는다.
유효하지 않은 벡터(길이 오류, NaN, 0벡터)는 로그에 얼굴 ID를 남기고 제외한다.
512개 이상에서는 IVF_FLAT 검색 인덱스를 생성한다.

## API

기존 웹 로그인 쿠키 또는 `X-Api-Key`를 사용한다.

```http
GET /api/v1/assets/1/faces
```

해당 사진에서 조회 가능한 얼굴 목록과 각 얼굴의 `faceId`, `assetId`, 위치(x/y/width/height),
personId/name/clusterId를 반환한다. 벡터는 반환하지 않는다. 얼굴이 없으면 빈 목록이다.

```http
GET /api/v1/faces/11/similar?limit=20&minSimilarity=0.55
```

반환 구조:

- `source`: 선택한 얼굴. 사진 전체가 아니다.
- `matches`: 얼굴별 후보(`face`, `similarity`). 동일 사진의 여러 얼굴도 별개 항목이다.
- `people`: 후보 중 SQLite에서 인물 ID가 연결된 얼굴만 인물 ID별로 묶는다.
  인물별 최고 유사도와 근거 얼굴 ID를 제공한다. 이름이 같아도 personId가 다르면 합치지 않는다.
- `indexedFaces`: 로컬 인덱스 행 수. 정확한 전체 인물 수/사진 수가 아니다.
- `notice`: 확정 인물이나 확률이 아니라 추천 후보임을 안내한다.

소스 얼굴과 같은 사진에 있는 모든 얼굴은 후보에서 제외한다. 함께 찍혔다는 이유로
동반자를 같은 사람으로 추천하지 않기 위해서다. 새 얼굴은 자기 벡터가 인덱스에 아직 없어도
SQLite의 현재 벡터로 기존 얼굴 후보를 조회할 수 있다.

`minSimilarity`는 0~1, `limit`은 1~50이다. 기본 0.55는 기존 cosine distance eps 0.45에 대응하는
초기 기준이며 검증된 동일인 판정 기준이 아니다. 최대 200개 검색 후보를 현재 SQLite 상태로
검사한 뒤 limit개를 반환한다. 후보가 없으면 빈 목록이며 가장 가까운 사람을 강제로 선택하지 않는다.

검색 후에도 현재 숨김·휴지통·영구 삭제·사진 종류와 벡터 fingerprint를 재검사한다.
재분석으로 얼굴 ID가 재사용되거나 벡터가 바뀐 오래된 결과는 제외한다.
인물 이름과 연결은 조회 시 SQLite에서 가져오므로 이름 수정은 인덱스 재생성 없이 반영된다.
소스가 삭제/숨김이면 404, 요청 중 소스 벡터가 바뀌면 409, 서비스 비활성이면 503이다.

## 이번 변경의 범위

얼굴 인덱스와 읽기 전용 후보 조회 API를 추가한다. 자동 인물 연결, 기존 DBSCAN 교체,
화면의 후보 선택 기능, 이름 기반 MCP 검색 도구는 이번 변경에 포함하지 않는다.
기존 얼굴 인식/군집화/사용자 확정 연결은 그대로 유지한다.

## 검증

```powershell
cd ml-worker
.venv-search\Scripts\python.exe -m unittest test_search_service test_face_search -v
.venv-search\Scripts\python.exe smoke_search.py --jar ..\server\build\libs\homephoto-server-0.1.6-rc2.jar --java <java.exe>
```

다중 얼굴 독립 저장, 동일 사진 제외, 숨김·삭제·ID 재사용, 실패한 순회의 인덱스 보존,
인증·모델/벡터 검증, 최신 이름 조회를 검사한다. 스모크 검사는 생성 사진 3장에 합성 얼굴 벡터를
2개씩 저장하고 실제 JAR → 동기화 → LanceDB → 얼굴별 후보 API를 검사한다.
이는 인식 정확도나 실제 사람을 구분하는 성능 검증이 아니다. 운영 배포 후 실제 사진으로 기준을 평가해야 한다.

롤백: 검색 서비스를 종료하고 `homephoto.search.enabled=false`로 되돌린다.
SQLite의 얼굴 벡터와 인물 정보를 삭제하거나 다시 분석할 필요는 없다.
