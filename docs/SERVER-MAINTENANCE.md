# 웹 서버 종료와 GitHub 업데이트

설정 화면의 서버 정보에서 릴리즈를 확인하고, 하단 버튼으로 서버를 안전하게 종료하거나 재시작한다. 종료 대상은 HomePhoto 서버 프로그램이며 PC 종료 기능은 아니다.

## 업데이트 순서

1. `GitHub 릴리즈 확인`을 누른다. 기본은 정식 버전이며 RC 버전은 사전 릴리즈 포함을 선택한다.
2. 현재보다 새로운 버전의 `다운로드·검증`을 누른다.
3. 검증 완료 후 `업데이트 적용 후 재시작`을 누르고 확인한다.
4. 화면은 새 서버 인스턴스가 응답하면 새로고침한다. 접속이 돌아오지 않으면 서버 로그와 `updates/apply-*/helper.log`, `result.json`을 확인한다.

고정 저장소 `cafealpa/homePhotobackupPjt`의 공개 GitHub Releases를 사용한다. GitHub API가 제공한 SHA-256, 다운로드 크기, JAR 시작 클래스와 빌드 버전을 검증한다. 체크섬이 없는 파일과 현재 이하 버전은 자동 설치하지 않는다. 조회/다운로드만으로 설치되지는 않는다.

자동 설치는 Windows에서 배포 JAR로 실행한 서버에 지원된다. IDE/Gradle 실행이나 `build` 출력물을 직접 실행한 경우 설치 버튼이 비활성화된다. 운영에서는 배포 폴더의 `homephoto-server.jar`를 실행한다. 개발용 `server/start-server.bat`는 루트 배포 JAR가 없으면 `build/libs`를 `run`에 다시 복사하므로, 개발용 `run` JAR를 업데이트했어도 이 배치로 다시 시작하면 로컬 빌드가 적용된다.

## 종료와 데이터 보존

- 종료 준비 중 새 요청에는 HTTP 503과 Retry-After를 반환한다. 상태 조회는 계속 가능하다.
- 진행 중인 HTTP 요청과 로컬 업로드 이관·썸네일·캡션·가져오기 등의 작업을 기다린다. 최대 120초를 넘기면 종료를 취소하고 요청 처리를 재개한다.
- DB에 저장된 대기 작업과 `incoming` 파일은 보존된다. 서버를 다시 시작하면 각 큐의 기존 복구 정책으로 처리를 이어간다.
- 외부 ML 워커는 별도 프로세스이므로 종료하지 않는다. 종료 준비 중 새 작업 배정은 중단한다.
- 업데이트 직전에 연결된 SQLite DB를 `VACUUM INTO`로 백업하고 작업 디렉터리의 `config`를 복사한다. 백업이 실패하면 현재 서버를 종료하지 않는다.
- 보조 프로세스가 기존 서버 종료를 확인한 후 실행 JAR만 교체한다. 사진, DB, 설정, incoming, ML 워커 및 기타 실행 도구는 릴리즈 ZIP에서 덮어쓰지 않는다.

## 작업 모니터링과 개별 제어

대시보드의 모니터링에서 원본 저장, 썸네일 생성, 얼굴 인식, 장면 분석, 문서 OCR,
사진/텍스트 검색 인덱싱, Google Photos 전송, 폴더/키즈노트 가져오기,
썸네일 폴더 이전/정리, 휴지통 자동 정리의 13종 작업을 관리한다.

- 작업 대기, 실행 차례 대기, 실행 중, 재시도 대기, 중지 중, 중지 완료, 재시작 중,
  처리 완료, 확인 필요, 비활성 상태를 구분한다. 전체량을 모르는 작업은 대기 수를 미확정으로 표시한다.
- 중지는 새 작업과 자동 재시도를 막는다. 실행권/외부 호출 대기는 취소할 수 있지만
  파일 확정, DB 커밋, 외부 게시 확정은 안전 경계까지 기다린다. 실행 기록이 모두 정리돼야 중지 완료가 된다.
- 재시작은 기존 실행 정리가 끝난 뒤 남은 작업을 재개한다. 확정된 실패는 별도의 재시도 버튼으로 처리한다.
  Google Photos의 게시 결과 미확인(UNKNOWN)은 자동 재시도하지 않는다.
- SQLite 큐는 계속 작업의 기준이다. 서버 재기동 시 RUNNING만 복구하고 FAILED와 시도 횟수/오류는 보존한다.
- `storageRoot/process-monitor/state.json`에 중지 상태, 최근 이벤트, 오류, 재시도 시각,
  가져오기 경로/모드 및 진행 기록을 보존한다. 중단된 가져오기는 중지 상태로 복구하여 화면에서 재개한다.
  파일 목록은 다시 스캔하고 이미 저장한 자산은 해시로 중복 제거한다.
- 진행 기록은 5초마다 저장하며 가져오기 접수/종료 및 제어 요청 시에도 저장한다.
  비정상 종료 직전의 표시용 진행 수는 최대 저장 주기만큼 뒤처질 수 있다. 실제 완료 여부는 DB/파일을 다시 확인한다.
- `homephoto.background-cpu-tasks`는 백그라운드 CPU 작업 동시 실행 한도다(기본 2, 범위 1–64, 재시작 후 적용).
  썸네일 변환, 얼굴 추론, OCR 이미지 준비, 사진/텍스트 임베딩이 공유하며 항목/청크마다 실행권을 반환한다.
  공정한 실행권 대기를 사용하고 원본 수신/저장과 웹 검색은 이 CPU 한도에 묶지 않는다.
  Gemini는 기존 공통 단일 호출/할당량 대기를 유지하며 호출 차례를 화면에 표시한다.

검증: `ProcessMonitorTest`, `ProcessControlIntegrationTest`에서 자원 대기 취소, 중지/재시작 경계,
영속 복구, 실패 보존, 작업별 상태 집계와 가져오기 재개를 확인한다.

## 업데이트 실패 시 확인과 복구

`updates/apply-*`에는 DB 스냅샷 `photos.db`, 설정 백업 `config`, 교체 전 `previous.jar`, 보조 프로세스 로그와 결과가 남는다. 다운로드 파일은 `updates/release-*`에 남는다. 이 폴더에는 설정 정보가 포함될 수 있으므로 서버 계정에 맞게 접근 권한을 관리한다.

새 Java 프로세스를 시작하지 못하면 이전 JAR로 복구한다. Java가 시작된 뒤의 애플리케이션 기동 실패는 자동 복구하지 않는다. 새 버전이 이미 DB를 마이그레이션했을 수 있기 때문이다. `result.json`의 STARTED는 프로세스 실행 성공이며 서버 정상 기동을 보장하지 않는다.

기동 실패 시 로그를 먼저 확인하고 서버가 종료된 상태에서 이전 JAR와 DB 백업의 호환성을 검토하여 복구한다. DB를 과거 스냅샷으로 되돌리면 이후 변경을 잃을 수 있으므로 자동으로 덮어쓰지 않는다. 서버가 완전히 종료된 뒤에는 웹에서 다시 시작할 수 없으며 서버 PC에서 실행해야 한다.
