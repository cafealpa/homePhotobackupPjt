# 얼굴 분석의 로컬 1600px 입력

2026-10-11부터 `FaceWorker`는 `ThumbnailService.thumbPath(hash, 1600)`로 찾은 기존 JPEG만
`FaceEngine.analyze()`에 전달한다. 검출과 얼굴 정렬·특징 추출이 모두 같은 썸네일 픽셀을 사용한다.
FACE 처리에는 `StorageAdapter` 접근, 원본 임시 복사, 400px 또는 원본 폴백이 없다.
썸네일 생성 작업 자체의 원본 접근은 기존대로 필요하다.

## 입력과 모델 계약

- 경로는 `ThumbnailStorage`의 설정 루트·샤딩·이전 폴더 조회를 재사용한다.
- `buffalo_l`의 `det_10g.onnx` / `w600k_r50.onnx`와 고정 SHA-256은 유지한다.
- 검출은 비율을 유지해 640×640에 패딩하고, 썸네일에서 5개 랜드마크를 정렬해 112×112를 추출한다.
- RGB NCHW, L2 정규화된 512차원 임베딩, 2048바이트 little-endian 저장,
  그룹화 코사인 임계값 0.55와 사용자 이름·이동·숨김 계약은 유지한다.
- DB 스키마·모델 변경이나 전체 재분석을 추가하지 않았다. 완료된 FACE/얼굴/인물 행은 보존한다.
  새로 처리하는 PENDING 또는 사용자가 실패 작업을 명시적으로 재시도한 경우부터 적용한다.
- 업로드·시작 백필의 PHOTO 전용 등록 정책을 유지하며, 잘못 남은 VIDEO FACE 작업도 선점하지 않는다.

## 썸네일 선후 관계와 대기

업로드는 THUMBNAIL과 FACE를 함께 등록한다. `JobQueueService.claim("FACE")`는 동일 자산의
THUMBNAIL이 PENDING/RUNNING/FAILED인 동안 FACE를 가져오지 않는다.
THUMBNAIL이 DONE이면 워커가 실제 1600px 파일도 확인한다. 오래된 DB에 THUMBNAIL 행이 없으면
기존 로컬 파일 확인은 허용하지만, 파일이 없을 때 생성이나 원본 접근을 시도하지 않는다.

| 상황 | FACE 상태·처리 | 확인/복구 |
|---|---|---|
| 생성 대기·진행 중 | PENDING 유지, 선점·분석·시도 증가 없음 | 생성 완료 후 다음 워커 주기에 자동 처리 |
| 썸네일 생성 FAILED | PENDING 유지, 분석 실패와 별도 집계 | 썸네일 작업을 재시도한 뒤 완료되면 자동 처리 |
| 완료 기록은 있지만 1600px 파일 없음 | PENDING 반환, 시도 증가 없음 | 로컬 파일/썸네일 경로 확인 후 60초 간격 재조회 |
| 오래된 DB에 썸네일 작업 없음 | 기존 1600px가 있으면 분석, 없으면 동일 대기 | 파일 또는 생성 작업 상태 확인 |
| 실제 추론 오류 | 기존 FACE 실패·재시도 정책 | 기존 실패 작업 재시도 |

파일 미준비는 기존 `jobs.last_error`의 준비 대기 표식과 `updated_at`으로 재조회 시각을 결정한다.
서버 재시작에도 대기 간격과 시도 횟수가 유지된다. 다른 준비된 사진은 계속 처리한다.
설정과 작업 모니터는 생성 대기·생성 실패·파일 확인 대기를 따로 표시한다.
이 표식은 모니터의 분석 실패 오류로 집계하지 않는다.

## 방향·비율과 좌표

ImageIO/Thumbnailator 경로는 EXIF 방향을 픽셀에 적용하고 `.size(size, size)`로 종횡비를 유지한다.
출력은 EXIF 방향이 없거나 정상 방향인 JPEG이며, OpenCV에서 다시 회전하지 않는다.
ffmpeg 경로는 기본 자동 회전을 사용하고 `scale=min(size,iw):-2`로 비율을 유지한다.
이 기존 경로는 **가로 폭을 제한**하므로 세로 사진의 `1600` 파일은 긴 변이 1600보다 클 수 있다.
이번 변경은 기존 썸네일 픽셀·생성 크기 정책을 바꾸거나 파일을 다시 만들지 않는다.

얼굴 좌표는 입력의 실제 너비·높이에 대한 0~1 정규화 좌표다. 검출용 640 패딩 좌표를 그대로
저장하지 않는다. 기존 `FacesController.faceThumb()`는 같은 방향의 1600/400 썸네일 크기에
정규화 좌표를 곱하고 35% 여유를 주어 크롭한다. 기존 얼굴 결과에도 같은 계약을 적용한다.
과거 파일의 잘못된 방향이나 잘못 저장된 좌표를 이번 변경이 자동 보정하지는 않는다.

## 검증 범위와 품질 비교

- 실제 SQLite와 원본 접근 금지 mock: 로컬 1600 입력, 400/원본 폴백 없음,
  생성 PENDING/RUNNING/FAILED 대기, 파일 미준비의 재시작·60초 재조회, 다른 작업 진행,
  시도 횟수 유지, 기존 완료 결과 보존과 명시적 재시도, 동영상 제외를 검증한다.
- 합성 JPEG의 EXIF 1~8: 두 썸네일 크기의 비율·픽셀 방향, 실제 OpenCV 디코딩,
  기존/신규 정규화 좌표로 기존 얼굴 크롭 API가 같은 색상 영역을 반환하는지 확인한다.
- ffmpeg가 설치된 환경에서는 회전 EXIF를 가진 JPEG를 HEIC 확장자로 등록해 실제 ffmpeg 분기와
  세로 이미지 비율·크롭을 검증한다. 실제 HEIC 코덱·동영상 검출 품질 시험은 아니다.
- 워커 테스트의 얼굴·임베딩은 모의 추론 결과다. 이 결과로 실제 인물 구분 품질이나
  네트워크/메모리/처리 시간의 절감 수치를 보장하지 않는다.

실제 사진 비교에는 같은 사진의 원본과 기존 1600px를 동일 모델로 분석하고 얼굴 수·검출 위치,
같은 인물의 원본/썸네일 벡터 코사인 유사도, 기존 그룹과의 매칭 및 다른 인물 오탐을 비교해야 한다.
작은 얼굴, 여러 사람이 있는 사진, 회전·HEIC 사진, 어둡거나 흐린 사진을 포함한다.
640px 검출 크기는 같지만 JPEG 축소·압축과 112px 정렬에 쓰는 얼굴 픽셀의 감소로 임베딩은
기존 원본 분석과 달라질 수 있다. 특히 작은 얼굴은 인물 구분 품질 비교가 필요하다.
운영 DB를 변경하지 않는 별도 입력으로 비교하며, 이번 작업에서는 운영 사진 전체 재분석을 하지 않는다.
