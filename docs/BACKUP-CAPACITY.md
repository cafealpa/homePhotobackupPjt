# 백업 수신 공간 보호

원본 저장소 연결이 끊겨도 서버가 수신 완료한 파일은 incoming에 보존한다. 공간 부족을 해결하기 위해 이미 인수한 파일을 자동 삭제하지 않는다.

## 기본 정책

- 최소 여유: 20GiB 또는 디스크 전체의 10% 중 큰 값.
- incoming 상한: 100GiB. DB에 없는 고아 파일, LOST/BLOCKED, 삭제되지 않은 완료 사본도 실제 파일 크기로 집계한다.
- 재개 여유: 5GiB. 중단을 유발한 파일 크기까지 고려하여 디스크 여유가 하한보다 충분히 높아지고 대기 용량이 상한보다 충분히 낮아져야 재개한다.
- 전송 예약: HTTP Content-Length를 기준으로 요청당 최대 3배의 디스크 공간을 예약한다. 멀티파트 임시 파일, 해시 계산용 사본, 동기 원본 저장 사본을 보수적으로 반영한다. 실제 예약과 검사에는 단일 락을 사용한다.
- 멀티파트 임시 파일 위치: 로컬 storage-root/tmp/multipart. OS 기본 임시 디스크와 수신 디스크가 달라 보호가 빗나가지 않도록 고정한다.
- 업로드 크기가 없는 chunked 요청은 411, 허용 요청 크기를 초과하면 413으로 거절한다. 앱은 길이를 지정하여 전송한다.

설정 화면의 백업 수신 공간 보호에서 기준을 수정하고 저장한다. 설정은 서버 config/application.yml의 homephoto.upload-buffer에 기록한다. DB 변경은 없다.

## 서버와 앱의 동작

1. 앱은 서버 대조 후 업로드 전 /api/v1/backup-capacity를 확인한다. 공간 확인 API가 없는 구형 서버(404)는 기존 방식으로 전송한다.
2. 서버는 인증 후, 멀티파트 본문 파싱 전에 실제 공간을 다시 검사·예약한다. 사전 조회만으로 공간이 보장되지는 않는다.
3. 부족하면 HTTP 507, code=BACKUP_STORAGE_FULL, Retry-After=300을 반환한다. 공간 확인 실패도 수신을 막는다.
4. 앱은 병렬 전송을 중단하고 서버 공간 확보 대기로 표시한다. 해당 항목을 신규 실패나 완료로 기록하지 않는다. 이미 수신된 다른 파일은 다음 해시 대조에서 확인한다.
5. 수동 백업의 대기는 WorkManager에 남겨 앱 화면이 닫혀도 재확인한다. Wi-Fi(비과금)·배터리 여유 조건에서 최초 5분 후 시작하고 지수 백오프로 재시도한다. 자동 백업도 대기 상태에서는 재시도 횟수 제한 없이 재시도한다. OS 절전 등에 따라 실행 시각은 늦어질 수 있다.
6. 자동 재개 취소 버튼은 수동 백업에서 등록한 공간 대기 작업을 취소한다. 별도로 설정한 정기 자동 백업은 유지된다.

앱의 SERVER_QUEUED(서버 수신 완료/원본 저장 대기)와 UPLOADED(원본 저장 완료)는 구분한다. 현재 앱에는 백업 완료 후 기기 사진 자동 삭제 기능이 없고 이번 변경에서도 추가하지 않는다.

## 디스크가 실제로 가득 찬 경우

예약은 다른 프로그램이나 썸네일/로그의 쓰기를 제한하지 못하므로 물리적인 가득 참을 완전히 방지하는 디스크 쿼터는 아니다. 디스크 부족 예외가 발생하면 507로 전달하고 해당 요청의 미완성 임시 파일은 기존 업로드 정리 경로로 제거한다. 이미 incoming으로 확정된 파일은 DB 기록이 실패했더라도 삭제하지 않는다. 고아 사본도 용량 집계에 포함한다.

원본 저장 큐는 신규 수신이 중단되어도 계속 재시도하므로 저장소 연결이 돌아오면 incoming 용량을 줄일 수 있다. 모델 다운로드·업데이트·다른 프로그램의 파일을 정리하거나 저장 공간을 늘리는 것도 가능하다. DB/config와 기존 수신 완료 파일을 임의로 지우지 않는다.

웹 설정과 관리 대시보드에 수신 가능 여부, 차단 이유, 실제 디스크 여유, incoming 사용량/상한, 전송 예약량을 표시한다. 실제 디스크를 채우지 않고 가짜 용량 프로브와 임시 서버로 경합·507·재개·파일 보존을 검증한다.
