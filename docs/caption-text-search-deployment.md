# JVM 설명 의미 검색 운영 배포 가이드

이 문서는 `520c69ef08efb771e66600d760224b412de0b866` 배포본을 기존 HomePhoto 서버에 적용하는 운영자용 절차다. 실제 운영 OS, 설치 폴더, 서비스 이름, 실행 계정과 DB 위치는 확인되지 않았다. 아래 명령의 `D:\HomePhoto`, `D:\HomePhoto-stage`, `D:\HomePhoto-search-index`는 모두 예시이며 실제 환경으로 바꿔야 한다.

배포 대상은 **Windows x64, Java 21**이다. 현재 배포 JAR에는 Linux/macOS 네이티브 라이브러리가 제외되어 있으므로 다른 OS에는 이 배포본을 그대로 사용하지 않는다. 이 문서를 작성하면서 운영 서버 중지·교체·재시작을 수행하지 않았다. 각 실행 단계는 운영자가 진행한다.

모델 구조·라이선스·체크섬·품질 측정은 [JVM 설명 의미 검색](caption-text-search.md), 일반 JAR 업데이트 방식은 [JAR 직접 배포](../deploy/README.md)를 참고한다.

## 1. 배포 파일 준비

```text
<운영 설치 폴더>/
  homephoto-server.jar
  homephoto-face-runtime-26d8632bfcc2016f3ce93c9bbb226d38e6a7839f13a24ba5f08060dd7c1b1ba2.jar
  models/caption-e5/
    model_quantized.onnx
    tokenizer.json
    model-manifest.json
```

- 서버와 보조 런타임 JAR는 같은 폴더에 둔다. 서버 Manifest의 `Class-Path`가 해시가 포함된 런타임 파일명을 참조하므로 이름을 바꾸지 않는다. 런타임에는 ONNX도 있으므로 얼굴 기능을 쓰지 않아도 필요하다.
- 해당 커밋 서버 JAR의 SHA-256은 `d8a856d57ec69559f5b9c3ad9f0fd25b01168cf0e1775efca1c7e58e0c268d3e`이다. 배포 시 동반 `.sha256`과 실제 파일 해시를 비교한다. 다른 버전에는 그 버전의 체크섬을 사용한다.
- 모델 두 파일 합계는 약 129.1MiB다. 실행에 직접 필요한 파일은 ONNX와 tokenizer이며 manifest는 배포 이력용으로 함께 보관한다. 모델은 서버 JAR에 포함되지 않는다.
- **서버 시작 시 모델을 자동 다운로드하지 않는다.** 검증된 모델 세 파일을 복사하거나 아래 선택적 준비 스크립트를 실행한다.

```powershell
# 저장소 루트에서 실행하는 예시. 운영 폴더와 분리된 준비 위치 사용
.\prepare-caption-model.ps1 -ModelDir 'D:\HomePhoto-stage\models\caption-e5'

# 준비한 서버 JAR의 체크섬 확인 예시
Get-FileHash -LiteralPath 'D:\HomePhoto-stage\homephoto-server.jar' -Algorithm SHA256
```

`prepare-caption-model.ps1`은 고정 리비전의 두 파일을 다운로드하고 SHA-256을 검증한 후 manifest를 생성한다. 유효한 기존 파일은 다시 받지 않으며 다운로드 검증이 끝난 뒤 파일을 교체한다. 기본 출력은 스크립트 위치의 `deploy/models/caption-e5`다. 서버를 시작하지 않는다.

소스에서 다시 빌드해야 할 때는 저장소 루트의 `build-jar.ps1`을 사용한다. 테스트 후 JAR와 체크섬을 준비하며 모델 준비는 별도 단계다.

### GitHub 업데이트 스크립트의 현재 제약

이 가이드 기준 커밋은 로컬 커밋이며 원격으로 푸시하지 않았다. 따라서 **현재 이 커밋을 `update-server-jar.ps1`로 원격 다운로드하는 방식은 사용할 수 없다.** 로컬에서 준비한 파일을 전달하는 절차를 사용한다.

추후 운영자가 해당 커밋을 원격에 게시한 뒤에만 아래 방식을 선택할 수 있다.

```powershell
# 해당 커밋이 GitHub에 게시된 이후에만 사용. 설치 위치는 예시
.\update-server-jar.ps1 -InstallDir 'D:\HomePhoto' `
  -Ref '520c69ef08efb771e66600d760224b412de0b866'
```

스크립트는 서버와 런타임 JAR를 검증하고 이전 서버 JAR를 `.bak`으로 남긴다. 기존 런타임도 롤백용으로 보존한다. 모델·설정·DB·키·사진을 갱신하지 않으며 서버 중지·시작도 하지 않는다. 기본 설치 위치는 `E:\homePhotoServer`이므로 실제 위치를 명시한다.

## 2. 실행 위치와 설정 확인

**상대경로는 JAR 파일 위치가 아니라 서버 프로세스의 작업 폴더 기준이다.** 기존 작업 폴더를 바꾸면 모델뿐 아니라 `config/application.yml`, 상대경로 DB·키 위치가 달라질 수 있다. 기존 실행 계정, 작업 폴더, Java 실행 파일, JVM 옵션과 외부 설정 인수를 기록하고 유지한다.

`server/start-server.bat`는 자신의 폴더로 이동한 후 실행한다. 그 폴더의 `homephoto-server.jar`를 우선 선택하고, 없으면 개발 빌드 경로를 찾는다. 운영 시작 대신 저장소의 개발용 시작 스크립트를 실행하지 않는다. 이 배치 파일은 전달받은 추가 인수를 서버에 자동 전달하지 않는다.

| 설정 키 | 기본값 및 동작 |
|---|---|
| `homephoto.caption-search.enabled` | `true` |
| `homephoto.caption-search.model-dir` | `models/caption-e5` |
| `homephoto.caption-search.index-dir` | 빈 값이면 `<homephoto.storage-root>/caption-search` |
| `homephoto.caption-search.min-similarity` | `0.80` |
| `homephoto.caption-search.max-score-gap` | `0.06` |

`index-dir`는 인덱스의 **루트 폴더**다. 실제 인덱스는 그 아래 `multilingual-e5-small-761b726d-int8-mean512-v1`에 만들어진다. 모델 ID까지 설정값에 넣으면 그 아래에 같은 이름의 폴더가 추가된다.

다음은 절대경로 인수를 사용하는 실행 예시다. 기존 운영 시작 명령을 통째로 대체하지 말고, 기존 옵션을 보존하면서 필요한 인수만 반영한다. 서비스나 작업 스케줄러를 사용한다면 해당 시작 정의에 반영한다.

```powershell
# 경로는 예시. 실행은 운영자가 교체 완료 후 수행
Set-Location -LiteralPath 'D:\HomePhoto'
java -Dfile.encoding=UTF-8 -jar .\homephoto-server.jar `
  '--homephoto.caption-search.model-dir=D:/HomePhoto/models/caption-e5' `
  '--homephoto.caption-search.index-dir=D:/HomePhoto-search-index'
```

실행 계정에는 모델 읽기, 인덱스 폴더 생성·수정, 기존 SQLite 쓰기 권한이 필요하다. 네이티브 라이브러리를 추출하는 계정의 임시·캐시 폴더에도 쓰기 권한이 필요하다. 기존 DB·설정·키의 권한을 불필요하게 넓히지 않는다.

DB 위치는 `spring.datasource.url` 직접 지정이 우선이며, 다음으로 `homephoto.db-path`, 미지정 시 `<homephoto.storage-root>/db/photos.db`다. `homephoto.db-path`는 DB 파일이 아니라 **폴더**다. 설치 폴더 아래에 DB가 있다고 가정하지 않는다. 이번 배포를 위해 기존 저장소·DB·키 설정을 바꿀 필요는 없다.

## 3. 백업, 정상 중지, 파일 교체

1. 기존 시작 방법과 Java 버전을 확인한다. 검증 기준은 Java 21 x64다. 전달받은 JAR·모델 체크섬을 교체 전에 확인한다.
2. 기존 운영 방법으로 HomePhoto를 정상 중지하고 종료를 확인한다. 저장소의 `stop-server.bat`는 8080 포트를 점유한 프로세스를 강제 종료하므로 일반적인 정상 종료 절차로 사용하지 않는다.
3. 중지 상태에서 이전 서버·런타임 JAR, 시작 정의, 외부 설정, 키 파일, 실제 DB 디렉터리를 접근 제한된 백업 위치에 보존한다. SQLite의 `photos.db`와 남아 있는 `-wal`·`-shm`은 일관된 세트로 보관한다. 실행 중 DB 파일 하나만 복사하는 방식은 피한다.
4. 사진 원본과 기존 저장소 백업도 확인한다. 기존 인덱스를 재사용·복원할 계획이면 중지 상태의 인덱스 폴더도 함께 보존한다. 인덱스는 다시 만들 수 있지만 DB의 원본 설명은 별도 보존 대상이다.
5. 검증한 보조 런타임 JAR를 먼저 배치하고 서버 JAR를 교체한다. 수동 복사 시 이전 JAR를 별도 백업해 둔다. 기존 모델 파일이 다르다면 먼저 보존한 후 준비된 세 파일을 배치한다.
6. 기존 DB·사진·설정·키 파일은 그대로 둔다. 개발 PC의 `data`, `config`, 키 파일을 운영 폴더에 덮어쓰지 않는다.
7. 운영자가 기존 시작 방법으로 서버를 재시작한다. 작업 폴더와 실행 계정을 유지하고 절대경로 인수가 필요한 경우에만 반영한다.

## 4. 시작 후 확인과 장애 시 대체 동작

서버 시작 약 15초 뒤 로컬 임베딩 작업이 시작된다. 빈 인덱스면 기존 `captions`를 큐에 등록하고 한 작업자가 최대 32개씩 처리한다. 설명 생성·수정·삭제 및 사진 삭제·복구는 이후 증분 반영된다. 중단된 작업은 재처리한다.

이 작업은 **기존 설명·태그만 사용하며 Gemini 호출이나 사진 재분석을 하지 않는다.** 다만 서버의 다른 분석 작업은 기존 설정을 따르므로, 새 사진 분석을 원하지 않으면 기존 워커의 일시정지 상태도 확인한다. JVM 장면 검색에는 Python 검색 서비스 시작이 필요하지 않다. 기존 이미지 의미 검색·얼굴 유사검색의 Python 경로는 이번 변경에서 제거하지 않았다.

기존 서버 주소의 `/scenes.html`에서 다음을 확인한다.

- `설명 의미 검색 (로컬 JVM)`의 인덱스 수가 증가하고 최종적으로 `준비됨`이 되는지 확인한다.
- 분석 완료된 유효 사진 수와 인덱스 수가 예상대로 맞는지 확인한다. 설명이 없는 사진은 의미 검색 대상이 아니다.
- 대표 검색어를 입력하고 `단어·설명 의미 검색을 합쳤어요` 안내가 표시되는지 확인한다.
- 기존 사진 조회·업로드 등 주요 기능도 확인한다.

모델 누락은 `모델 파일 필요`, 초기화 실패는 사용 불가 상태로 나타나며 단어 검색은 계속 동작한다. 모델 파일 경로·체크섬·권한과 보조 런타임 배치를 확인한다. 실패 후 약 60초 간격으로 재시도한다. 모델 파일만 보완하면 재시작 없이 복구될 수 있으며 검색 후보 캐시는 최대 30초 유지된다. 오류가 계속되면 무관한 설정을 바꾸기 전에 상태와 경로부터 확인한다.

개발 PC에서는 모델 배치 후 재시작 없이 55장 준비 완료, `공원에서` 16장과 `자전거 타는` 5장 결과를 확인했다. 이는 운영 서버 또는 대규모 데이터 검증 결과가 아니다.

## 5. 롤백과 DB 변경 주의

의미 검색만 임시 비활성화하려면 기존 시작 인수에 다음을 적용하고 운영 절차대로 재시작한다. 단어 검색은 유지된다.

```text
--homephoto.caption-search.enabled=false
```

JAR 롤백은 서버를 중지한 뒤 보존한 이전 서버 JAR 또는 해당 `.bak`을 `homephoto-server.jar`로 복원하고, 이전 런타임 JAR와 시작 설정을 유지하여 재시작한다. 런타임 JAR는 서버 Manifest가 참조하는 이전 이름의 파일이 있어야 한다.

### 추가되는 SQLite 객체

이번 커밋은 의미 검색 초기화 시 다음 객체를 `IF NOT EXISTS`로 추가한다.

| 객체 | 용도 |
|---|---|
| `caption_search_changes` 테이블 | `asset_id` 기본키와 `version`을 가진 증분 큐 |
| `caption_search_insert` 트리거 | `captions` INSERT |
| `caption_search_update` 트리거 | `captions` UPDATE |
| `caption_search_delete` 트리거 | `captions` DELETE |
| `caption_search_visibility` 트리거 | `assets`의 `deleted_at`, `purged_at`, `media_type` UPDATE |
| `caption_search_asset_delete` 트리거 | `assets` DELETE |

이번 변경은 기존 설명 데이터나 열을 파괴적으로 변경하지 않지만, **이전 JAR로 돌아가거나 기능을 비활성화해도 이 객체는 남는다.** 자동 역마이그레이션은 없으며 남은 트리거는 계속 큐를 기록할 수 있다. 큐 테이블만 삭제하면 남은 트리거 때문에 쓰기가 실패할 수 있으므로 임의로 삭제하지 않는다. 이전 버전과의 운영 호환성을 무조건 보장하지 않는다.

정확히 배포 전 DB 상태로 돌아가야 한다면 서버를 중지하고 일관된 DB 백업을 복원한다. 배포 이후 생성된 데이터는 사라지므로 먼저 보존·복구 범위를 판단한다. DB 백업을 복원할 때에는 그 DB와 맞는 인덱스 백업을 쓰거나 별도의 빈 `index-dir`에서 다시 색인한다. 더 최신 인덱스를 그대로 재사용하면 큐와 내용이 어긋날 수 있다. 기존 인덱스는 복구가 끝날 때까지 보존한다.

이 문서는 해당 커밋의 변경을 다룬다. 훨씬 오래된 운영 버전에서 업그레이드한다면 중간 버전들의 DB 변경과 롤백 조건도 별도로 검토한다.

## 6. 초기 부하와 검색 품질 확인

20~30만 장 실측 성능은 아직 검증하지 않았다. 30만 개의 원시 벡터만 약 439MiB이며 HNSW 그래프·문서·세그먼트·재빌드 여유 공간이 추가된다. 실제 메모리에는 JVM, ONNX 가중치, mmap과 OS 캐시가 포함된다.

별도 검증 환경이나 점검 시간대에 인덱스 증가 속도, 서버 프로세스 메모리·CPU, 디스크 여유, 대표 검색 응답 시간과 기존 기능 지연을 기록한다. 이 버전에는 문서화된 운영용 색인 건수 제한 설정이 없으므로, 소수 데이터만 먼저 검증하려면 분리된 검증 환경을 사용한다. 운영 DB를 임의로 잘라내지 않는다. 소규모 smoke 측정치를 전체 데이터 성능으로 해석하지 않는다.

현재 검색 제한과 판단 기준은 다음과 같다.

- 의미 후보 최대 200개, 화면 페이지당 40개, 후보 캐시 최대 30초.
- 기본 코사인 유사도 0.80 이상이며 최고점과 차이 0.06 이내인 후보를 선택한다. 이 값은 초기 휴리스틱이며 확률이 아니다. 단어 일치 결과에는 이 조건이 적용되지 않는다.
- 정렬은 단어·의미 양쪽 일치 → 단어만 일치 → 의미만 일치 순서다. 전체 결과가 하나의 의미 점수순은 아니다. 화면에 점수는 표시하지 않는다.
- 실제 대표 검색어의 누락·오탐을 확인한다. 설명에 없는 사물은 텍스트 임베딩으로 복구할 수 없다.

## 7. Git과 보관 범위

모델·인덱스·DB·키·사진은 Git에 넣지 않는다. 기본 모델·실행 데이터 경로는 `.gitignore`에 포함되어 있지만 임의의 사용자 지정 경로까지 자동 제외되는 것은 아니다. 인덱스에는 개인 설명 정보가 포함되므로 DB와 마찬가지로 접근을 제한한다. 운영 데이터는 별도 백업 정책으로 보관한다.
